## DAY 01

- **栏目**：一图看懂
- **标题**：AI Agent 不只是“提问→回答”：它还要做什么？
- **正文**：很多人第一次听到 AI Agent，会把它理解成“我提问，模型回答”。这个理解没错，但只覆盖了最表面的一层。一个能帮你完成工作的 Agent，还要把请求接进来，把上下文整理好，交给模型判断下一步；如果模型决定调用工具，系统还要执行工具、拿回结果，再让模型继续判断。Hermes Agent 的结构可以先粗略看成：入口 → Agent Core → 模型/工具/策略 → 记忆与运行环境。入口可以是 CLI、TUI、桌面端或消息网关；工具可以连接浏览器、终端和文件；记忆负责保存会话与可检索信息。重点不是“模型多聪明”，而是这些部分能不能形成稳定闭环。今天先记住一句话：聊天是接口，Agent 是一套会观察、决策、行动、再观察的系统。后面 29 天，我会用普通职场人听得懂的方式拆开它。

## DAY 02

- **栏目**：Agent 拆解
- **标题**：Hermes Agent 的四个入口：同一个大脑，不同的门
- **正文**：如果你只在命令行里见过 Agent，可能会以为它只能在终端工作。Hermes Agent 的入口并不只有一个：可以从 CLI/TUI 进入，也可以通过 Electron Desktop 使用，还能由 Telegram、Slack 等消息平台的网关接收请求，另外还有 API/ACP 这类面向集成的入口。它们的界面和传输方式不同，但不应该各自重新发明一套“思考逻辑”。更合理的做法是：入口负责接收消息、显示状态和处理平台差异，公共的 Agent Core 负责上下文、模型请求和工具调用。对普通使用者来说，这意味着你可以在电脑上开始一个任务，再换到消息平台继续沟通；对开发者来说，入口层和核心层分开，维护成本更可控。这里说的是代码结构和主要控制流，不代表所有平台都天然共享同一份会话。真正的会话边界，还要看配置和接入方式。

## DAY 03

- **栏目**：Agent 拆解
- **标题**：Agent Core 到底在做什么？不是“另一个模型”
- **正文**：Agent Core 可以理解成 Agent 的中枢，但它不是一个更大的模型，也不是一段神秘提示词。它要做的事情很工程化：接收当前请求，组织上下文，调用模型，解析模型是否要使用工具，把工具结果放回对话，再决定是否继续这一轮。模型擅长根据信息做判断，Core 负责把判断变成可执行的流程。它还要面对一些模型本身不会替你解决的问题，例如消息角色如何保持正确顺序、工具失败后怎么返回、会话状态放在哪里，以及什么时候结束本轮。Hermes 把这些共性流程尽量放在共享核心里，让 CLI、桌面和网关复用，而不是每个入口各写一套循环。对职场人来说，可以把它类比成项目协调人：不亲自完成每项工作，但负责把需求、专家、工具和结果按顺序接起来。Agent 是否可靠，往往取决于这个“协调层”是否清晰。

## DAY 04

- **栏目**：一图看懂
- **标题**：模型负责思考，工具负责行动：别把两者混为一谈
- **正文**：让 Agent 变得有用，通常不是再给模型塞一段更长的说明，而是给它合适的工具。模型可以判断“需要查文件”“需要运行命令”或“需要打开网页”，但真正读取文件、执行终端命令、操作浏览器，靠的是工具和运行环境。一个简单的流程是：模型提出结构化的工具调用，工具系统校验参数并执行，把结果返回给模型，模型再根据结果继续下一步。这样分工有两个好处：第一，行动可以被记录、限制和审计；第二，换模型时，工具接口仍然可以保持相对稳定。Hermes 的工具编排层就是连接模型意图和实际动作的地方。也要注意，工具不是越多越好：每个工具都会增加选择成本和边界问题。对普通职场任务，先提供少量清晰工具，通常比把几十个能力一次性堆给模型更容易维护。好的 Agent 不是“什么都能做”，而是知道什么时候该行动、行动到哪里该停。
- **配图建议**：左右两栏“模型：判断/规划”“工具：读取/执行”，中间用像素蓝箭头连接，底部标注“结果回传”。

## DAY 05

- **栏目**：开发现场
- **标题**：我为什么开始研究 Hermes Agent？因为“会聊天”还不够
- **正文**：我开始认真看 Hermes Agent，不是因为想再找一个聊天机器人，而是因为工作里的很多任务本来就不止一步：整理资料、查看文件、运行检查、记录结果，最后还要把结论交付给人。只会生成文字的模型，在这些环节之间需要人不断复制粘贴；有了 Agent，模型、工具、记忆和执行环境才有机会连成流程。研究的过程也让我意识到，真正难的不是画一个很酷的架构图，而是确认每一层的职责：入口不要承担核心循环，模型不要直接拥有无限权限，记忆不要变成无边界的历史堆积，插件也不要反过来绑架核心。Hermes 对我有吸引力的一点，是它同时面对 CLI、TUI、桌面端和消息网关，工程问题会被真实地暴露出来。这个账号不会把它包装成万能助手，而是记录我看到的结构、实验和失败。对普通职场人来说，最有价值的可能不是某个“神奇提示词”，而是一套能解释为什么有效、什么时候会失效的方法。

## DAY 06

- **栏目**：Agent 拆解
- **标题**：Memory 和聊天记录不是一回事：Agent 为什么需要记忆？
- **正文**：聊天记录是“发生过什么”的连续文本，Memory 更像是从历史中整理出来、以后可能有用的信息。比如一次对话里提到你偏好的报告格式，这句话可以留在原始会话中；如果系统经过合适的处理，把它作为可检索的偏好保存下来，下一次任务才可能被找到并使用。Hermes 的会话状态和记忆能力可以分开理解：SessionDB/检索层负责保存和查找信息，Agent Core 决定什么时候把相关内容带进当前上下文。这里有一个重要边界：记忆不是越多越好。无关内容会干扰当前任务，过时信息会误导模型，敏感信息还需要更谨慎的存储策略。对职场人而言，可以先从少量稳定偏好开始，例如输出格式、项目术语和长期目标，不要把所有聊天都当成永久记忆。今天的结论是：聊天记录回答“以前说过什么”，记忆要回答“现在什么值得被想起”。

## DAY 08

- **栏目**：Agent 拆解
- **标题**：Agent Loop：一次请求为什么不一定只调用模型一次？
- **正文**：普通聊天常见的流程是：发消息，收到回答。但 Agent 处理任务时，模型可能需要多次观察和行动。一个简化的 Agent Loop 是：读取当前上下文 → 请求模型 → 如果模型给出普通回答，就结束；如果模型请求工具，就校验并执行 → 把工具结果加入上下文 → 再请求模型判断下一步。比如你让它“检查一个项目并总结问题”，它可能先列目录，再读取文件，再运行检查，最后才组织结论。循环的价值在于让模型看到真实结果，而不是只凭猜测一次性作答。循环也带来风险：工具失败、参数错误、任务没有终点，都会让系统卡住或产生额外动作。因此可靠实现需要明确停止条件、错误返回和权限边界。Hermes 的核心循环正是把这些步骤编排起来。对使用者来说，看到 Agent 连续调用几次工具并不一定代表它“变聪明了”，更应该看每一步是否有必要、结果是否被正确利用。

## DAY 09

- **栏目**：一图看懂
- **标题**：Model Router 是什么？不是“随机换模型”
- **正文**：当一个 Agent 可以连接多个模型提供方时，就需要回答一个现实问题：这次请求交给谁？Model Router 可以理解成模型路由层，它根据配置、任务类型、可用性或用户选择，把请求送到合适的模型。它不等于“哪个模型都自动选得最好”，更像交通调度：先知道有哪些路线，再根据规则选一条能走的路。路由层还要处理提供方的接口差异、流式输出、模型名称和错误信息，让上面的 Agent Core 不必为每个提供方写一套循环。Hermes 的架构把 Model Router 放在核心与模型提供方之间，这种分层有利于替换模型而不重写工具和会话逻辑。对普通职场人，实用的判断方式是：写作、总结、代码和长任务可能需要不同取舍，但不要把“更贵”直接等同于“更适合”。先定义任务要求，再根据可用模型和配置做选择，并记录失败原因，才是可复用的路由经验。

## DAY 10

- **栏目**：开发现场
- **标题**：Tool Registry 为什么重要？工具多了，先要找得到
- **正文**：工具一多，问题就从“有没有功能”变成“Agent 能不能准确找到并调用它”。Tool Registry 可以理解成工具的登记处：统一收集工具名称、描述、参数 schema、执行入口以及必要的可用性检查。Agent Core 从注册表发现工具，模型看到的是结构化定义，执行层再负责真正调用。这样做比在多个文件里手写一长串 if/else 更容易扩展，也更容易检查工具是否重复、参数是否不一致。Registry 还可以成为边界的一部分：有些能力只有在服务配置好、权限满足时才应该暴露给当前会话。要注意，注册表不是权限系统的替代品，也不是把所有工具无条件塞进提示词的理由。它解决的是发现和编排，权限、确认和运行环境仍然要单独设计。对普通职场流程，可以把它类比成公司的服务目录：目录写得越清楚，协作成本越低；但目录里有入口，不代表每个人都拥有执行权限。

## DAY 11

- **栏目**：Agent 拆解
- **标题**：Skills、Plugins、MCP：都是扩展，但不是同一种扩展
- **正文**：这三个词经常被放在一起说，但可以先用一个朴素的方式区分。Skill 更像一份可复用的工作方法或说明，让 Agent 知道某类任务应该怎么做；Plugin 更像可插拔的程序能力，可以把新的后端或功能接入系统；MCP 则是一种把外部工具/资源以标准方式提供给模型客户端的协议和服务器形态。它们的边界会因项目实现而有差异，所以不要只看名字，最好确认具体仓库的加载方式、权限和生命周期。Hermes 的设计倾向是让核心保持稳定，把新增能力放在边缘：能用 skill 表达的，不必改核心；需要外部服务或独立集成的，可以考虑 plugin 或 MCP。这样做的好处是降低核心每次请求都要承担的工具和维护成本。对普通使用者来说，Skill 更接近“操作手册”，Plugin 更接近“可安装模块”，MCP 更接近“标准化的外接服务”。理解这个区别，选工具时就不容易把概念混成一团。

## DAY 13

- **栏目**：失败复盘
- **标题**：一个看似合理但不工作的想法：把所有能力都塞进核心
- **正文**：我曾经很容易被一种想法吸引：既然 Agent 未来要做很多事，那就把浏览器、记忆、自动化、各种服务都直接写进核心，调用起来最方便。问题是，核心会快速变成一个巨大的“万能房间”。每增加一种能力，所有入口、配置和测试都可能被牵连；每次请求都要面对更长的工具清单，模型选择也会变得更难；某个服务不可用，还可能影响本来不需要它的用户。这个想法失败的地方，不是功能不能实现，而是放错了层。Hermes 更值得借鉴的取舍是“核心做窄，能力做宽”：把稳定的 Agent Loop 和通用编排留在核心，把新增能力优先放到 skill、plugin、MCP 或服务侧。这样不是拒绝扩展，而是把扩展放到更合适的边缘。我的结论是，判断一个功能要不要进核心，先问三件事：是否几乎所有请求都需要？是否无法由现有扩展承载？是否会增加每轮调用的长期成本？

## DAY 14

- **栏目**：周总结
- **标题**：做 Agent 最容易低估的三件事：边界、状态和成本
- **正文**：第二周看了 Agent Loop、路由、工具注册和扩展机制，我越来越觉得，做 Agent 最容易低估的不是模型调用，而是三件基础工作。第一是边界：工具能读什么、改什么、在哪个环境执行，需要明确；没有边界，“自动化”很快会变成不可控。第二是状态：会话、工具结果、长期记忆和配置不是同一类数据，混在一起会让下一轮判断变得含糊。第三是成本：每次请求都会携带工具和上下文，频繁改变系统提示或工具集合，还可能破坏长期对话的缓存收益。Hermes 把入口、Core、工具、记忆和运行环境分层，正是在给这些问题找位置。这里没有一个“配置完就永远正确”的答案，真正的工程实践是持续记录：这一步为什么执行、失败后返回了什么、哪些信息值得保留。下一周我会做几个小实验，比较无工具和有工具、无记忆和有记忆、单 Agent 和多 Agent。实验不追求漂亮数据，只看差异是否能被解释。

## DAY 15

- **栏目**：Agent 实验室
- **标题**：不用工具 vs 使用工具：Agent 的答案差在哪里？
- **正文**：今天做一个很小、但很容易说明问题的实验：给 Agent 一个需要查看真实资料的任务，先限制它只能根据对话回答，再允许它读取指定文件或运行必要检查。前一种情况下，模型可能给出结构清楚的建议，但它无法确认文件里的实际内容；后一种情况下，它可以先获取事实，再基于结果回答。这个实验并不是为了证明“有工具一定更好”，因为工具也可能读错路径、返回空结果或带来权限风险。我要观察的是三件事：模型有没有主动识别信息缺口；工具调用是否与任务相关；拿到结果后，最终回答有没有引用或解释这个事实。对普通职场人，这对应一个很常见的场景：让 AI 总结一份真实表格，和让 AI 凭经验猜表格内容，可靠性不是一回事。结论先写在这里：工具的价值不在于让模型看起来更忙，而在于让它接触到当前任务的真实世界。发布时我会附上脱敏流程图，不虚构准确率或性能数字。

## DAY 16

- **栏目**：Agent 实验室
- **标题**：有记忆 vs 无记忆：记住越多真的越好吗？
- **正文**：这次实验不比较“谁更聪明”，而是观察记忆在一个连续任务里的作用。先让 Agent 完成一次任务，在对话中明确一个长期偏好，例如报告采用固定结构；第二次任务分别使用没有历史信息的上下文，以及检索到这条偏好的上下文，然后看它是否正确采用格式。实验还要加一个反例：放入一条过时或与当前任务无关的信息，观察它会不会把旧内容当成硬规则。这样才能看出记忆的两面性。好的记忆可以减少重复说明，坏的记忆会把噪声带进当前判断。Hermes 的 SessionDB/检索能力提供了保存和查找的基础，但“什么应该记住、什么时候取出、取出后是否可信”，仍然是产品和流程问题。对职场人，我建议先记稳定偏好，不要默认保存所有私人对话；每条记忆最好有来源和更新时间。我的实验结论不会写成“记忆让效率提升了百分之几”，只记录可复现的输入、检索结果和行为差异。

## DAY 17

- **栏目**：Agent 实验室
- **标题**：单 Agent vs 多 Agent：人多不一定办事快
- **正文**：多 Agent 听起来像“把任务分给几个人”，但真实成本也会一起增加。单 Agent 处理一个边界清晰的任务时，状态集中、沟通少，调试相对直接；多 Agent 可以把资料检索、代码检查、结果汇总等工作拆开，但需要定义角色、输入输出、失败处理和最终合并方式。我的小实验会选择一个可以拆分、又能由单 Agent 完成的任务：先让一个 Agent 从头做到尾，再让两个角色分别完成子任务，最后由汇总角色整理。观察重点不是谁的输出更长，而是有没有重复劳动、信息有没有在传递中丢失、最终结论是否更容易核对。Hermes 支持 subagents 等并行工作思路，但“能并行”不代表“应该并行”。对普通职场流程，如果任务本身依赖同一份上下文，拆成多个 Agent 可能只是增加协调；只有当子任务边界清楚、结果可以独立验证时，多 Agent 才值得考虑。结论：先把单 Agent 的流程做稳，再谈编排团队。

## DAY 18

- **栏目**：开发现场
- **标题**：让 Agent 操作终端会发生什么？先别急着给最高权限
- **正文**：终端工具让 Agent 从“给建议”进入“执行动作”，也把风险带进来了。一个真实流程可能是：模型提出命令，工具层接收参数，运行环境执行，结果和错误回到 Agent，再由它决定是否继续。这里至少有几个需要确认的问题：命令在哪台机器执行？当前目录是什么？是否会修改或删除文件？超时后怎样停止？输出里有没有敏感信息？Hermes 把本地、Docker、SSH、Singularity、Modal、Daytona 等环境作为不同的执行后端来考虑，重点不只是“能不能跑”，还包括动作落在哪个边界里。对职场人，最稳妥的使用方式是先让 Agent 读取和检查，再允许它做可逆修改；涉及删除、发布、发信或生产系统时，保留人工确认。终端不是魔法按钮，权限越大，越需要日志、隔离和停止条件。我的开发记录会展示命令类别和确认流程，不展示真实密钥或敏感项目内容。

## DAY 19

- **栏目**：Agent 实验室
- **标题**：本地环境和远程沙箱：区别不只是“电脑在哪里”
- **正文**：同一个 Agent 任务放在本地和远程沙箱执行，差异至少有四层。第一是文件可见性：本地可能直接看到工作目录，远程环境则需要挂载、上传或初始化。第二是权限边界：本地动作可能影响个人文件，沙箱通常更适合承载试验性操作，但具体隔离程度要看实现。第三是依赖和网络：两边的工具、版本、凭据和访问范围不一定相同。第四是结果回传：远程产生的文件、日志和状态，必须有清晰的取回方式。Hermes 的运行环境抽象把 Local、Docker、SSH、Modal、Daytona 等后端放在能力层之下，说明“执行在哪里”本身就是架构选择，而不是一个无关紧要的参数。今天的实验会固定同一任务和输出要求，只记录哪些前置条件需要改变、哪些路径不可见、失败是否可解释，不杜撰安全等级或速度排名。对普通职场人，选择原则很简单：涉及个人和生产数据先确认边界，涉及未知代码优先考虑可丢弃、可重置的环境。

## DAY 20

- **栏目**：失败复盘
- **标题**：Agent 为什么会“自信地做错”？因为它缺少验证闭环
- **正文**：模型输出很流畅，不代表它看到的事实完整。Agent“自信地做错”，常见原因包括：没有调用能提供事实的工具，把猜测当成结论；工具返回了空结果或错误信息，但系统没有显式标记；上下文里有过时记忆，模型把它当成当前规则；任务没有验收条件，最后一步只是生成一段看起来完整的文字。解决方式不是一句“请谨慎”，而是给流程增加可观察的闭环：先说明依据，再执行动作；工具失败要返回失败，而不是伪装成空白成功；关键结果要用第二步检查；高风险动作保留人工确认。Hermes 的 Agent Loop、Tool Orchestrator、Policy 和 Memory 分层，恰好可以分别放置这些控制点。对普通职场人，可以把验收写得很具体：数字是否来自哪份表、文件是否真的生成、链接是否能打开、发送前是否让我确认。我的结论是，可靠性不是让 Agent 永远不犯错，而是让错误更早暴露、更容易回滚，也不把不确定性包装成确定答案。

- **正文**：第三周做了四个方向的观察，我给自己的实验记录定了一个简单模板。先写问题：到底想验证工具、记忆、协作还是执行环境的哪一点？再写条件：输入是否相同，哪些能力开启，模型和配置有没有变化？接着记录过程：调用了哪些工具，返回了什么，在哪一步需要人工介入？最后写结论和限制：看到的差异能解释到什么程度，还有哪些因素没有控制？这个模板看起来不复杂，但能避免把一次偶然成功包装成普遍规律。比如“有记忆”实验只能说明某条检索信息在当前任务里被使用，不等于所有记忆都有效；“多 Agent”实验能展示协作成本，也不代表单 Agent 永远更好。Hermes 让我更关注系统的实际链路：入口、Core、模型、工具、状态和运行环境之间有没有断点。对普通职场人也可以这样做复盘：任务目标、输入材料、AI做了什么、你检查了什么、下次改哪一步。真正可复用的不是一句夸张结论，而是一份别人能照着重做的过程。

## DAY 22

- **栏目**：观点
- **标题**：为什么 Agent Core 要保持“窄腰”？小核心，大生态
- **正文**：我越来越认同“核心做窄，能力做宽”这句话。所谓窄腰，不是让 Agent 变弱，而是让所有入口都只依赖少数稳定的共性：上下文怎么组织、模型怎么请求、工具调用怎么循环、状态如何衔接。其他能力，比如新的平台、新的服务、新的任务方法，尽量在边缘扩展。这样做的现实好处是，CLI、桌面端和消息网关可以共享核心逻辑，新增能力也不必每次改动所有入口。更重要的是，模型每轮都要面对工具和上下文，核心里塞入太多偶发能力，会增加长期维护和选择成本。Hermes 的入口层、Agent Core、工具编排和能力层可以用这个视角理解。窄腰也不是绝对规则：真正基础、广泛需要、现有扩展无法承载的能力，才值得进入核心。对普通职场人，可以把它类比成公司流程：把审批、记录等共性做成稳定底座，把不同团队的业务留在模块里。底座越清楚，变化越容易接入。

## DAY 23

- **栏目**：观点
- **标题**：新能力应该放进插件，而不是核心？先看它是不是共性
- **正文**：我并不是认为所有新功能都应该做成插件。更实用的判断方式，是先看这个能力的用户范围、变化频率和依赖边界。如果它几乎每次请求都要用，且是 Agent Loop 不可替代的一部分，进入核心有理由；如果它服务特定平台、特定团队或外部产品，插件、skill、MCP 或服务侧通常更合适。这样做可以让核心保持稳定，也让能力拥有自己的配置、版本和故障边界。以 Hermes 为例，新增消息平台不应该要求所有用户都理解该平台；新增某类专业服务，也不应该让每次请求都携带一大段无关定义。插件化还会带来新的责任：加载过程、权限、兼容性和升级都要说明，不能把“可插拔”当成自动安全。对普通职场人，这像给公司加系统：通用报销流程适合平台化，少数团队的特殊表单不必塞进全员首页。我的观点不是追求最少代码，而是让每段代码有清楚的归属和边界。

## DAY 24

- **栏目**：Agent 拆解
- **标题**：一个可靠 Agent 需要哪些边界？不是只加一句提示词
- **正文**：可靠边界至少要分成几层看。能力边界：模型能看到哪些工具和数据；权限边界：工具可以读、写、删除或发送什么；环境边界：动作是在本地、容器、SSH 还是其他沙箱执行；状态边界：哪些内容属于当前会话，哪些可以长期保存；交付边界：什么时候需要人工确认，什么结果必须经过检查。只在系统提示里写“不要做危险操作”，通常不够，因为真正的权限还在工具和运行环境。Hermes 的 Policy、Tool Registry、Memory/State 与执行后端可以分别承载这些问题。对普通职场人，最简单的实践是把任务分级：阅读和总结可以自动做；改文件先显示 diff；发消息、删数据、改生产配置必须确认。还要让失败可见：权限不足、路径不存在、服务不可用，都应该明确返回。边界不是给 Agent 戴手铐，而是让它知道自己能做什么、不能做什么，并让人能在关键节点接管。自动化越深入，边界越应该写成流程，而不是愿望。

- **栏目**：观点
- **标题**：我不太看好的三种 Agent 设计：看起来强，实际难用
- **正文**：第一种是“全能但无边界”：工具很多、权限很大，却没有清楚的确认和回滚，演示很惊艳，日常不敢用。第二种是“全靠长提示词”：把所有规则写进一段巨长文本，却没有结构化工具、状态和验证，遇到真实变化就容易失效。第三种是“只展示成功路径”：视频里每次都顺利完成，却不说明工具失败、网络中断、记忆过时和权限不足时会怎样。它们共同的问题，是把 Agent 当成一次性输出，而不是一个需要长期维护的系统。Hermes 的架构让我更关注核心循环、工具编排、Policy、记忆和运行环境之间的关系：模型只是其中一环。对普通职场人，选择 AI 工具时也可以问三个问题：失败时我看得见吗？它做了什么有记录吗？我能在关键动作前接管吗？我不反对复杂能力，反对的是复杂性被藏起来。一个真正值得放进工作流的 Agent，应该允许你理解它，也允许你暂停它。

- **正文**：从架构视角看，Hermes Agent 的优点很清楚：多个入口可以复用 Agent Core；工具、记忆、技能、插件和运行环境有相对明确的分层；本地、容器、SSH 等执行方式让“在哪里工作”成为可配置问题；同时保留 CLI、TUI、桌面和消息网关等不同使用方式。这些设计适合持续实验和扩展。局限也同样真实：系统组件多，初学者需要先建立整体心智模型；不同模型提供方和执行后端可能带来配置差异；工具越丰富，权限、状态、错误处理和调试越需要自己理解；某项能力是否可用，还取决于具体配置和环境，不能只看架构图就下结论。我不把这些局限写成“产品不行”，它们是通用的工程取舍：能力越多，边界和学习成本通常也会上升。对普通职场人，建议从一个低风险任务开始，确认入口、工具、结果和人工检查都走通，再逐步增加自动化，不要一上来就把全部权限交出去。

- **栏目**：一图看懂
- **标题**：我理想中的 AI Agent 架构：清楚、可查、能停
- **正文**：如果让我用三个词描述理想的 Agent 架构，我会选：清楚、可查、能停。清楚，是入口、核心、模型、工具、记忆和执行环境各有职责，不需要靠猜。可查，是每次重要工具调用都有输入、结果和错误记录，长期记忆有来源和时间，最终结论知道依据在哪里。能停，是遇到高风险动作、权限不足、循环无终点或结果不确定时，系统能够暂停并交给人判断。Hermes 的主要控制流可以画成：多入口 → Agent Core → Model Router/Tool Orchestrator/Policy → Memory、Skills、Automation 和 Sandbox。这个图不是某个产品的完整实现承诺，而是我用来检查设计的思维模型。模型能力会更新，工具会替换，入口会增加，但这三条原则仍然适用。对职场人，理想架构并不意味着你要自己搭一套复杂系统；你可以把它变成选型问题：能不能看懂它做了什么？能不能追溯依据？关键动作前能不能停下来问我？

## DAY 28

- **栏目**：观点
- **标题**：Agent 最难的不是模型，而是把闭环做完整
- **正文**：模型很重要，但一个 Agent 能不能真正工作，往往卡在模型之外。请求从哪里进来？上下文是否包含了当前任务真正需要的事实？工具定义是否清楚？参数错误怎么处理？执行环境是否安全？结果有没有回到循环里？记忆是否把旧信息误当成新规则？完成后谁来验收？这些问题任何一个断掉，模型再会生成文字，也只能得到一个“看起来像完成”的结果。Hermes 的价值，正是把这些环节放到同一套架构里观察：入口、Agent Core、Model Router、Tool Orchestrator、Policy、Memory 和 Runtime 各自承担一部分闭环。对普通职场人，这个观点很实用：选 AI 工具时不要只问“它用的是什么模型”，还要问“它能不能接触真实资料、执行必要动作、反馈失败并让我检查”。模型负责提出可能的下一步，系统负责让下一步真实发生、结果返回、错误暴露。Agent 的竞争力，不只是一句回答有多漂亮，更是整个闭环能不能稳定地服务一个具体任务。

## DAY 29

- **标题**：30 天前后，我对 Agent 的变化：从功能清单到责任地图
- **正文**：30 天前，我更容易用功能清单理解 Agent：能聊天、能搜索、能跑命令、能记忆、能接插件。现在我更习惯画一张责任地图：入口负责接入，Core 负责循环，模型负责判断，工具负责行动，Policy 负责边界，Memory/State 负责必要的历史，Runtime 负责动作落点，Skill、Plugin、MCP 和自动化负责扩展。这个变化看起来只是换了几个词，但会直接影响排查问题的方式。回答不对，可能不是模型差，也可能是资料没读到；工具没执行，可能不是 Agent 不会，而是注册、权限或环境出了问题；下一次没有延续，也不一定是记忆功能失效，可能是检索范围和当前会话不匹配。过去一个月我也更确定：不该虚构性能数据，不该把架构图当成完整部署图，更不该把一次成功演示当成稳定能力。接下来我会继续记录真实实验、失败和配置差异。希望这个账号留下的不是“AI很神奇”，而是遇到问题时，大家知道先检查哪一层。
